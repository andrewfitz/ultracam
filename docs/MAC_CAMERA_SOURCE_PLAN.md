# Mac Camera capture source

Proposed implementation. Add **Mac Camera** under `Vendors/MacCamera/` alongside Blackmagic, with plugin ID `maccamera`. One AVFoundation capture plugin serves the built-in FaceTime camera, USB webcams such as Logitech, iPhones using Continuity Camera, and third-party cameras published to macOS. A feed selects a specific device. The goal is the earliest usable video sample macOS exposes, at the selected capture mode, before Ultracam applies any effects. A camera or its driver may already have decoded, cropped, tone-mapped or otherwise processed that image.

Out of scope: screen capture, muxed (DV / iOS-screen) devices, following `systemPreferredCamera`, and vendor USB control requests.

## Where it fits in Ultracam

The vendor plugin owns discovery, hardware configuration and delivery of the first usable video and audio samples. Once admitted, a Mac Camera frame follows the same host routes as a DeckLink frame.

### Which stage performs a conversion

1. **At input**, request device-native samples. Negotiate another delivery representation only when the source itself needs decoding or its native buffer cannot enter Ultracam’s capture pipeline. Show the actual delivered subtype and any known loss under Input and Hardware. This decision changes what every consumer receives, including source recording. A source already admitted for capture stays native even if one output route refuses it.
2. **For live effects**, build the existing `PipelineConfiguration` from the feed settings and actual source declaration. `CaptureController` selects frames for the cap before allocating GPU work. `LUTProcessor` handles the enabled pixel operations. A user choosing 8-bit 4:2:0 or a smaller output is choosing the existing Color format or Output size effect. Apply that choice on the output branch without changing the device request. The Color format picker selects an output pixel layout and bit depth. Camera log, LUT edge declarations and Program color management keep their separate roles.
3. **For Effects Off**, preserve the admitted picture, dimensions, color interpretation and cadence. Leave saved effects in place. Source recording and the monitor source branch retain access to the admitted frame. The production live publishing path uses an owned, pixel-preserving GPU copy. If the extension cannot publish the bypass format, explain the route limitation and point to the appropriate Effects controls when an available effect can resolve it.
4. **At each destination**, use the negotiated feed output for the camera sink, the existing Program normalizer for Program, and the existing recording or stream encoder for codec-specific conversions. For example, a 1080p60 webcam can feed a source take at 1080p60 while live Effects produce 720p30 in 4:2:0. The device remains in its selected mode throughout.

## 0. Dependencies and host changes

The plugin contract fits, but the host has only ever run one source shape in production. Settle these before hardware work, using `FakeCapturePlugin` so a failure is attributable to the host and not to a camera. That fixture compiles only under test support, because the boundary lint rejects shipping fakes, and it scripts no audio today, so extend it first.

**Host gate.** Drive a scripted feed of 1920×1080 and 1280×720, `420v`/`420f`/`2vuy`, constant 30 fps, with unpaired Float32 mono 48 kHz and 44.1 kHz PCM, through bypass, preview/scopes, LUT, Program, source recording, Program stream and the virtual camera. Include one take where audio stays declared but packets stop and later resume; it fails today (see section 4) and becomes the regression for the interruption signal. Record each refusal. Known risks found in the current tree:

- No shipping plugin has sent unpaired audio. DeckLink declares `pairedWithFrames`; the unpaired route through `sourceAudio` to the writer's `ClockMappedPCMBridge` has only fixture coverage.
- [PLUGINS.md](PLUGINS.md) still states production capture is 4K `v210` only and that 1080p/720p input is not active. The typed path admits by `PixelFormatTable` and the 4K guards in `CaptureController` are now test-support only, so the statement looks stale. The gate decides; update PLUGINS.md with the result.
- Program pre-negotiation passes a `v210` passthrough format regardless of source (`AppModel.swift`, `requestProgramOutputPreNegotiation` and its neighbour).
- The camera extension has a finite format catalog covering 720p, 1080p, 4K UHD and 4K DCI, and `SourceSizeAdmission` refuses upscales by default. Update admission to evaluate the fitted picture scale independently of canvas size. Section 2 defines padding and magnification for fixed outputs.
- `CameraSink.validateCameraSource` refuses virtual-camera output for a variable-rate source, and the host infers drops only for constant-rate sources.
- Capture-qualified pixel formats a Mac camera can deliver are `420v`, `420f`, `2vuy`, `yuvs` and `BGRA`. 8-bit 4:2:2 bi-planar and every 10-bit bi-planar format have no table entry.
- Feed status takes presence and switcher activity from `.media` today. For a PCM-only feed, derive activity from the admitted packets and update the same statistics once per packet, even with the meter closed. Clear live presence and activity on mic loss while retaining cumulative counts and the take’s audio declaration. Keep DeckLink’s existing metadata accounting when it emits both metadata and PCM.
- Check how LUT, Program and recording treat `unspecified` and Rec.601 colour.

**Host changes this plan needs.** These are not in the plugin and are not small:

1. Mode and microphone selection. Production always starts with `CaptureTiming.automatic`; `.fixed` is used only by test support, `expectedFormat` has no app caller and `CaptureDeviceInfo.modes` is display text. See section 3 for the chosen route.
2. A camera permission flow. The usage string and entitlement exist, but nothing requests or reports camera authorization today.
3. Extend Settings › Hardware’s vendor editor and the inspector’s Signal detail. Share the existing stop-to-change rule and give microphone changes audio-specific wording.
4. Use an identity-group `DeviceFact` for Built-in, Continuity Camera, Desk View or Virtual Camera when identified. Report verified transport through `CaptureDeviceStatus.link` and its existing Hardware renderer. Leave an unknown link unlabeled and reserve the connector field for the source input connector.
5. Derive audio wording from the selected source in the inspector recording footer, strip/status, Settings › Audio and the streaming input picker. Preserve embedded-audio wording for DeckLink.
6. An asynchronous authorization step on the capture plugin contract, defaulted for existing plugins, plus the host's pending-start tracking (section 1). `AutomaticFeedPolicy` latches after one attempt and re-arms only through `retry()`.
7. An ordered audio interruption and resume signal (section 4). `CaptureEvent` has no such case. Add a dedicated audio-only writer operation. The existing whole-take resume also changes video cadence and the shared movie timeline, and the existing PCM resume retains interpolation history.
8. Take handling on a redeclaring epoch. Today the host marks the take failed (`rejectRecordingMetadata` → `failTakeMetadata`); it does not finalize it. For a valid new epoch, detach the old take at the sequence boundary, drain previously admitted work and finalize asynchronously. Preserve the existing failure path for malformed metadata. The plugin also has no view of take state, so anything "deferred until the take ends" must be decided by the host or signalled to the plugin.

**Build wiring.** `Vendors/MacCamera/vendor.json` with `kinds: ["capture"]`, system frameworks only and no `sdk` block. Declare `com.apple.security.device.camera` and `com.apple.security.device.audio-input` under `capabilities.entitlements`, and `NSCameraUsageDescription`, `NSMicrophoneUsageDescription` and `NSCameraUseContinuityCameraDeviceType` under `capabilities.infoPlist`, then extend `vendors.py check-capabilities` to validate SDK-less manifests even when SDK availability is false. Add regression cases for a missing declared key and for a Continuity opt-in that is missing, false or a string. Verify the built host carries Boolean true and retain the separate bundle checks. Add only the Continuity key to `Config/App-Info.plist`; the others exist. Add nothing to the camera extension's plist or entitlements (`test_future_input_declarations`). Register `MacCameraCapturePlugin()` in `VendorRegistry.capture`, regenerate the project, and extend the manifest, membership, bundle and reusable-conformance contract tests. Run `check-vendor-boundaries.py`: host-side changes must not name this vendor or its symbols. The project builds with complete strict concurrency and warnings as errors, so confine every AVFoundation object to one session queue.

**Integration with the existing host**

- Seed the saved capture format, rate and microphone UID through the registry’s synchronous `configureSettings` call before discovery. Resolve that selection at session open and verify it before delivering media. Automatic recording can start while the Hardware UI is still restoring its settings. A late restore must preserve the active selection.
- If the probe finds that macOS hides devices before authorization, expose **Enable Camera Access** on the Mac Camera entry in Settings › Hardware even with zero devices. Use the same permission request and refresh inventory on grant. Look up each assigned feed’s availability error by plugin ID. Keep aggregate driver warnings in the Hardware overview.
- At a valid epoch cutoff, close admission to the old take on the ordered capture path. Hand off once, by take identity, to the existing recording stop lifecycle for detach, drain, asynchronous finalization, finishing status, saved-file publication and error reporting.
- Route host-side CPU fallback through the existing **Allow CPU conversion (compatibility)** policy sampled at session start and its diagnostics. Report AVFoundation input-format negotiation in Hardware. Selecting a decoded input format grants no additional host CPU fallback permission.

## 1. Discover devices and prove what they deliver

Use an app-only vendor manifest, Swift sources and vendor tests following the Blackmagic layout. Implement `CaptureSourcePlugin`. Keep AVFoundation device discovery and session configuration inside the plugin, behind a small internal device/session protocol so vendor tests can script formats, samples and failures without hardware.

Discover with one `AVCaptureDevice.DiscoverySession` for `.builtInWideAngleCamera`, `.external`, `.continuityCamera` and `.deskViewCamera`, video media type only. The deployment target is macOS 26, so none of this needs availability checks. Label Continuity (`isContinuityCamera`) and Desk View devices. Include third-party virtual cameras and identify them when the system provides that information. Track arrivals and removals by observing the discovery session's device list, without opening idle cameras. Publish `shareable: false`, a `mayPause` tolerance for Continuity devices, and a `missingDeviceHint`.

Device IDs are `maccamera:<uniqueID>`. Persist that ID and reconnect by it. The probe must establish whether a USB camera's `uniqueID` changes with the port. Automatic reconnect requires a verified persistent identity. If the saved UID disappears or proves ambiguous across a port swap, mark the assignment missing. Model and display name may suggest a replacement. Save its new identity only after the user selects it.

Filter Ultracam's own outputs with `VirtualCameraDescriptor.isDeviceUID` during discovery and again at open. That predicate matches CMIO device UIDs. Confirm `AVCaptureDevice.uniqueID` is the same string for the legacy, Program and per-feed outputs, with a test, because a mismatch produces a feedback loop instead of an error.

Permission: `CaptureSession.start` is synchronous and cannot wait for a prompt. Expose an asynchronous authorization step before synchronous start. Track the pending start by feed, device ID and request generation for manual and automatic capture. Coalesce permission prompts. On grant, consume each pending request once and start only if its generation, assignment and demand are still current. Stop, reassignment or withdrawn demand invalidates it. A status refresh alone cannot rearm AutomaticFeedPolicy after a failed start. Map denied and restricted to driver status and a `PluginError` that names System Settings › Privacy & Security › Camera. Re-read authorization when the app becomes active.

Build a thin capture probe as the first milestone. For each test camera, enumerate device formats and their frame-duration ranges. Open a selected mode, inspect actual samples, then close the session. Record:

- device format, delivered media subtype, dimensions, pixel-buffer presence, IOSurface backing and color attachments;
- PTS, duration validity and observed cadence, including in low light where many webcams lower their rate;
- whether the format survives `startRunning`, and what it took (see section 2);
- unique ID across replug and port change, and the IDs of Ultracam's own outputs;
- whether devices and their formats enumerate before camera authorization;
- whether enumeration or format inspection wakes a Continuity iPhone.

Pass admitted CVPixelBuffers to typed frame delivery. Source admission validates layout. The live `LUTProcessor.submitPassthrough` additionally requires an IOSurface-backed input and copies its planes into an owned output. Test an ordinary CVPixelBuffer on each branch. If a route needs a bounded copy into shareable storage, account for it and classify it under the existing CPU pixel-access rules. Replace DeckLink-specific driver advice on the shared rejection path with an actionable device-neutral reason. Preserve ownership, timestamps and image interpretation across any copy.

This establishes which routes need implementation before promising a mode in the UI.

## 2. Negotiate the closest-to-native feed

- Start automatic mode with the saved per-device selection, falling back to the current usable format only on first use. If a saved mode is unavailable, show its status and let the user choose a replacement. A fixed choice pins a specific device format and a duration within that format's supported ranges. For fixed FPS, set both min and max durations in a single session configuration transaction and verify readback after capture starts. Use exact rational durations where advertised. Retain distinct formats at the same dimensions and FPS when their subtype, color space or other meaningful properties differ. Save a capability signature and re-resolve it on reconnect. Report a missing saved mode.
- Apply format and frame-duration changes under the device configuration lock on the session queue. `AVCaptureSession.Preset.inputPriority` is unavailable on macOS, so the session can replace the format when it starts. The probe must find the working sequence; the candidate is to hold the device lock across `startRunning`. Re-read the active configuration and verify incoming samples. Show requested mode, delivered mode and measured FPS separately.
- AVFoundation setters raise Objective-C exceptions that Swift cannot catch: `activeFormat` with a foreign format, an out-of-range frame duration, an unsupported focus, exposure or white-balance mode, and `addInput`/`addOutput` when not permitted. Check `formats`, the duration ranges, `is…ModeSupported` and `canAdd…` before every call. Add an Objective-C catch shim only if the probe shows a precondition is insufficient.
- Request device-format samples with `AVCaptureVideoDataOutput.videoSettings = [:]`. The full-size delivery switches (`automaticallyConfiguresOutputBufferDimensions`, `deliversPreviewSizedOutputBuffers`) do not exist on macOS, so compare delivered dimensions with the active format on every declaration. Avoid app-requested scaling, mirroring, stabilization, tone mapping and color conversion on ingest. [Apple video output settings](https://developer.apple.com/documentation/avfoundation/avcapturevideodataoutput/videosettings) · [Apple Continuity Camera guide](https://developer.apple.com/documentation/avfoundation/supporting-continuity-camera-in-your-macos-app)
- Surface observable upstream effects: Center Stage, Portrait, Studio Light, background replacement and reactions. Indicate when macOS owns the switch and keep system-wide and user-owned effects under user control. Recheck frame-duration ranges when Center Stage or Portrait changes, because both constrain the rate.
- An admitted image buffer goes directly into the existing immutable `CapturedPixelBuffer` delivery path. Preserve range, depth, chroma layout, color metadata and timing. Do not silently tag missing color metadata as Rec.709. Keep missing source tags unspecified where representable. Show the limitation for consumers that require an interpretation. Route an explicit RGB primaries/transfer declaration through the existing Camera log and LUT contracts; preserve physical transport facts such as range and matrix. Record any route-specific assumption at that route. Verify the actual buffer before advertising native delivery. Preserve the original capture frame independently of any downstream preview, recording or virtual-output conversion.
- When native delivery is unsupported, show the native subtype and the available decoded or converted formats. Prefer the closest admitted depth, chroma, range and HDR representation. Require an explicit choice for a fallback that loses precision, chroma detail or HDR. Scope that choice to the specific source mode and conversion. Prioritize native support for formats commonly observed on target cameras, especially when the available conversion loses image information. Qualify new pixel formats and their GPU routes under [the source format plan](SOURCE_FORMAT_PLAN.md).
- Preserve native dimensions and pixel aspect in bypass and source recording wherever supported. For a feed with **Effects › Output size** enabled, use its selected canvas and existing Fit/Crop policy. **Source size** in that picker resolves to the nearest published canvas. With **Fit**, the planned 1× cap for a smaller source needs a shared geometry change: expose the upscale option alongside output sizing when relevant and use the shared scaler for padding. Honor explicit Crop. Keep existing saved output choices and compatibility for existing feeds. Apply the same rule where Program needs its own canvas, once per required resize. Effects Off never silently pads a feed to satisfy the extension.

## 3. Integrate settings, timing and lifecycle

**Mode selection.** Use per-device vendor settings in Settings › Hardware, reachable from Inspector › Input. Present Capture Format and Frame Rate as two controls editing one requested mode. Commit the format signature and exact rational duration together under the device ID, apply them in one session configuration and read back both after capture starts. Keep the committed pair intact if an edit fails. Use the existing `CaptureTiming.automatic` entry point for Mac Camera. Keep microphone selection independent and leave output resize and rate cap under Processing.

During restore, resolve the saved format first and refresh its available rates before validating FPS. Update `VendorSettingsStore.restore()` to use the refreshed capabilities. Preserve a missing saved mode and report which part is unavailable. Offer standard rates, endpoints and Custom FPS for continuous ranges. Validate decimal or fractional input against the selected format’s advertised duration ranges. Idle edits save intent without opening the camera. Show the requested mode and verified running mode separately.

**Controls.** Reuse `VendorSetting` for the controls AVFoundation exposes on macOS: focus, exposure and white-balance mode where `is…ModeSupported` reports them. Check availability and writability for the selected device and mode, read back writes, surface errors and refresh dependent controls after a mode change. Keep automatic control modes available. Lens position, custom shutter/ISO, custom white-balance gains and `videoZoomFactor` are unavailable to a native Mac app and are not offered. Model-specific USB controls need IOKit access and an added sandbox entitlement; revisit only if hardware testing identifies a gap.

**Timing.** AVFoundation stamps every output of a session, video and audio, on the session's `synchronizationClock`. Use sample PTS on that clock and a verified mapping from it to host time. Declare the video clock domain from what the probe shows that clock to be: `hostTime` if it is the host clock, `deviceClock` otherwise. `SourceAdmission` requires a constant-rate frame's duration to equal the declared duration exactly, and a variable-rate frame's duration to lie inside the declared bounds.

- Preserve a valid sample duration and deliver immediately. Declare a verified fixed mode constant. A constant declaration admits only frames whose duration equals it exactly, so stamp the declared duration when the sample's is missing or differs by rounding. If actual timing changes, re-evaluate the declaration before publishing affected frames; that redeclaration is a new epoch and interrupts a take.
- Use the negotiated mode and live sample timing for every device, including a previously unseen model. Declare an automatic mode with a supported duration range variable when the camera can vary exposure cadence. If sustained delivered cadence diverges from a fixed declaration, verify the effective range and redeclare at the observed cadence. Count timestamp gaps as inferred and driver-reported drops as confirmed. A single gap alone cannot distinguish the two causes.
- Declare variable cadence with supported bounds. Only a missing duration requires holding one frame for a contiguous next PTS. At stop, reset or a gap, count an unresolved frame as discarded and release it. Report measured FPS, inferred PTS gaps and confirmed drops separately. An exposure-driven rate change is a cadence change.
- The virtual-camera sink currently refuses variable-rate input. Report that route limitation. Any future fixed-rate adaptation belongs at the output boundary and preserves the source timeline for bypass and recording.

**Epochs.** Every redeclaration is a new epoch with an explicit discontinuity: a mode change, an external format change, a Continuity rotation or effect that changes dimensions, a clock reset, and any audio declaration change. The host currently fails an active take on a redeclaring epoch ("start a new take"); at the first valid new-epoch declaration the host atomically detaches the old recording route before admitting media from the new epoch. Previously admitted work retains the old take identity through drain and asynchronous finalization. Preview and capture can immediately consume the new epoch. Invalid or stale deliveries retain their existing rejection behavior. State the interruption in the UI wherever a setting interrupts capture, and keep interrupting Hardware settings read-only while capture runs. Apply a user-requested change on the next capture start.

**Delivery and lifecycle.**

- `CaptureSession.start` is synchronous. Configure and call the blocking `startRunning` on the session queue, and return running or failed. Confirm the caller is never the main thread.
- Serialize format announcements, frames and audio under the existing sequence, epoch and clock contracts. Set `alwaysDiscardsLateVideoFrames`, count `didDrop` callbacks by reason and report them separately from host drops. Bound the delegate queue and retained buffers under the existing capture retention budget, because AVFoundation stops delivering when its pool is held. Drain callbacks on stop.
- macOS lets other apps open the same camera and change its format. Observe `activeFormat` and `isInUseByAnotherApplication`. On an external change, redeclare and say another app changed the mode; do not fight for the format.
- Handle `isSuspended`, session interruption and runtime-error notifications, unplug, Continuity pause/resume, sleep/wake and failed reconfiguration. Restore the previous working mode after a failed switch when possible. Keep assignments pinned across interruptions.
- Rely on `CaptureDeviceClaims` with `shareable: false` so two feeds cannot fight over one active format. Test simultaneous selection and claim release after a failed start.

## 4. Pair a microphone with the camera

Ship microphone pairing with the Mac Camera source. In the selected device’s Hardware settings, provide **Microphone** choices for Off, a system-linked microphone when available, and an explicitly selected audio input. Discover audio devices separately with `.microphone`. Use AVFoundation's macOS `linkedDevices` or an audio port on the chosen capture input as evidence of a physical association. If there is no unique match, let the user select the built-in, USB or Continuity microphone. Keep the user's choice per camera using the audio device UID. Default to Off until selected. Reconnect the saved device specifically, including when two microphones have identical names. [Apple device associations](https://developer.apple.com/documentation/avfoundation/avcapturedevice/linkeddevices)

Request microphone permission when the user enables audio, using the existing host entitlement and usage description. Add the selected input and an `AVCaptureAudioDataOutput` to the video session with explicit connections to the chosen ports. Verify that adding audio preserves the selected video format. A denied, missing or busy microphone leaves video available and exposes its status in the feed. Release its input on stop. `CaptureDeviceClaims` is keyed on capture devices, so keep a plugin-internal microphone claim to prevent two feeds from counting the same signal in automatic switching.

Inspect the audio sample description, channel layout, frame count, PTS and buffer list. Leave `audioSettings` nil to receive device-native samples, and preserve native linear PCM when it maps to a contract sample type; Mac microphones usually deliver Float32, often mono, at 44.1 or 48 kHz. For other representations, request PCM through `audioSettings` and report the conversion. Cap or refuse channel counts the meters and recorder cannot take, with a reason. Send immutable `CaptureAudioPacket` planes in the existing ordered delivery stream. Carry the actual sample rate, channel count, layout and interleaving. Preserve mono and expose the active system microphone mode. Route the packets through the existing meter, source recording and audio-driven switcher paths.

Pairing identifies hardware. Audio callback boundaries are independent of video frames. Audio shares the session clock with video, so declare an unpaired audio clock domain matching the video one, supply an explicit mapping, and leave `pairedFrameSequence` unset. Assign video and audio from the same session synchronization clock one `ClockInstanceID` and publish one verified session-to-host mapping for both bindings. Verify clock continuity on reconnection. If the clock changes and continuity cannot be established, create a new binding and follow the epoch transition in section 3. Recording then takes the existing clock-mapped PCM route, whose bridge defaults allow 2,000 ppm drift and 20 ms audio/video error. Serialize audio declarations, mapping updates and packets with video. Resolve disabled or unavailable audio to `.absent`.

Preserve the active take through a temporary microphone loss. The current PCM converter rejects a timestamp jump beyond its tolerance and the writer marks the take failed. Add an ordered audio-only interruption and resume signal through capture and recording. On loss, mark the mic unavailable in the UI and meters, keep video recording on its original timeline, and retain the take's audio format. On verified return of the same UID, format and compatible clock mapping, use the dedicated audio-only writer operation at the first returning packet. Clear pending PCM interpolation samples and fractional phase, anchor the new audio segment at the packet’s mapped time, and preserve video cadence, video timestamps and the shared movie offset. Preserve the elapsed gap on the movie timeline. Apply the same time checks if packets resume after a missed device notification.

If the returning mic changes format or clock continuity cannot be established, the first valid new-epoch declaration closes admission to the old take as described in section 3. The host drains and finalizes it while preview continues. If reattachment itself would disturb live video, the host defers it until the take ends. Use the same stop-to-change Hardware workflow for a user-selected microphone. Automatic recovery of the already assigned mic follows the audio interruption policy. A take stopped while the mic is still absent must finalize with all accepted video.

On a previously unseen device fixture simulate low-light 30-to-15 fps without a drop callback and verify measured cadence changes with zero confirmed drops. | Microphone identity and recovery | Test a USB webcam mic, a built-in mic and a Continuity iPhone mic. Verify linked and manual pairing, duplicate names, denied access, audio-only disconnect/reconnect and a blocked reassignment during a take. Unplug for several seconds. Play the finalized movie and verify continuous video through and after the gap, correct audio placement on return, and no stale meter or switcher signal. Inject distinct PCM values before and after the gap and check the first resumed samples for pre-gap bleed. Compare all recorded video timestamps with an uninterrupted control. Also stop during the gap and exercise changed-format and changed-clock recovery. |
| Audio fidelity and sync | Use injected mono/stereo PCM with known channel values and packet timing, at 44.1 and 48 kHz. Verify one clock mapping update reaches both bindings at the same sequence and independent PCM packets retain their own PTS. Check meters, switcher decisions and recorded track channels. For hardware, record a visible and audible sync cue at the start and end of a ten-minute take. Measure offset and accumulated drift separately. For the fixed-rate qualification take, require both absolute initial A/V offset and absolute change in offset over ten minutes to be at most one frame period at the tested FPS. Record both in milliseconds for each device pair. A pair exceeding either limit may qualify for capture, with measured offset and drift published. Reserve synchronized-recording qualification for pairs passing both limits. Include a constant 250 ms offset fixture to prove the first check fails even with zero drift. |

With Output size enabled and Fit selected, for a square-pixel 640×480 source on a 1280×720 canvas, verify a centered 640×480 picture by default and a centered 960×720 picture with upscaling enabled.
