# Stream the Program feed

The native macOS app publishes the switched Program picture and one fixed embedded audio feed to one RTMPS destination. Settings uses the existing app size, cadence and bitrate conventions. H.264 and HEVC use hardware encoding. AV1 uses software encoding. The original 1080p30 Rec.709 H.264 preset at 6 Mb/s is the migration default. Audio uses stereo AAC-LC at 48 kHz / 160 kb/s.

## During a show

1. **Set up once.** Open the existing Program status-bar popover and choose **Set Up Stream…**. Open a Streaming form in Settings with destination name, RTMPS server, masked stream key, audio input and editable video settings. Choose one enabled camera feed by stable feed ID. Its embedded audio stays selected across all cuts. A production mixer can supply this feed through a capture input that carries its audio. Show the selected stereo pair for multichannel inputs, duplicate mono to stereo, and provide explicit Video Only. Show input level during setup on demand. Save does not publish.
2. **Start deliberately.** Once configured, the same Program popover shows the destination, audio source and **Start Stream**. Mirror that action in the existing Program commands and menu bar item through the same UI action. Start is available with two or more enabled cameras, consistent with Program availability. Settings explains this requirement. If the session drops to one enabled camera, keep streaming the surviving Program source and keep status and Stop reachable in the status bar and menu. With no eligible source, use the picture-loss behavior below until stopped or a source returns. In manual capture mode, surface Start Capture when needed. In automatic mode, starting a stream supplies capture demand. Report missing credentials, an unavailable embedded feed or missing selected channels before publishing, with a direct remedy.
3. **Operate as usual.** Click a picture to select it, Cut to change Program, and use Auto or Hold as today. Picture changes follow committed Program cuts. The selected feed supplies audio over every cut, including while its picture is off Program. The Program status segment gains a compact Streaming indicator while active, visible with the popover closed and at narrow widths. Its popover shows destination, elapsed time, audio level and Stop Stream. Leave camera strips for camera actions. Maintain separate evidence for virtual-camera delivery and streaming. Show the Program on-air tally when either output is delivering fresh video. Show each destination's own health in the popover. Publisher evidence describes delivery to ingest; viewer playback is verified separately.
4. **Recover or stop.** Show Connecting, Streaming, Reconnecting or Failed in the same place. Route actionable failures through the existing session problem display. Closing the main window keeps the stream running. Stop Stream works during connection and recovery, and releases stream-owned resources. Extend existing stop-camera/quit protections to mention affected live video or fixed audio. Launch restores setup and starts idle.

Exercise the concrete publisher with an independent receiver. Inspect package resolution, app signing, third-party notices and library-internal buffering. The app already has outbound networking and audio-input entitlements. | 2. Give streaming independent Program demand | Extend AppModel’s programPicture condition, automatic capture, director demand and FeedRuntime pixel demand, as well as transport reconciliation. Keep the two-camera start rule distinct from demand for an already-running stream. Keep one cut scheduler and one committed selection. Branch immediately after ordered cut selection and Program-time mapping, before the virtual camera’s format, cadence and active-client gate. Preserve existing source readiness and failover policy. | 3. Deliver media on one clock | Establish a session epoch using Program time anchored to the host clock. Pace repeat frames on their output slots. Use existing GPU conversion to produce the pixel format required by the selected encoder profile, with matching color attachments. Verify SDR conversion of supported source color spaces, or refuse an unsupported conversion visibly. Send processed Program pixels, including output-applied looks. Monitor aids, tally and SwiftUI overlays stay local. Use a dedicated worker and bounded leases. Under pressure drop stale stream video, count it and resume at the current live edge. | On source loss, show No Program Picture as soon as fresh video is stale. After the existing bounded repeat window, emit black at stream cadence until a fresh frame returns. Keep selected audio running. Filler never counts as fresh Program video for tally. Verify the receiver shows black and resumes picture without a reconnect. A slow publisher cannot accumulate unbounded frames, stall capture or invalidate a camera lease. |
| 4. Supply fixed audio | Subscribe to the chosen feed’s capture PCM independently of recording and metering. Acquire its demand before checking for audio in automatic mode; release it on failed or cancelled start. Hold demand for that source across cuts. Normalize the selected channels to stereo PCM, map capture timestamps to the same session epoch and compensate for measured clock drift. Bound the audio queue by duration. Program supplies one media clock origin to the RTMP publisher at startup and after reconnect. Both tracks retain their offsets from that origin even if the encoder drops the first picture. Trim earlier media and fill known PCM gaps in timestamp order. Supply strictly increasing positive input times. Verify with deliberately staggered inputs in both orders. For a temporary audio loss after going live, insert timed silence, show Audio Missing and resume the same device on return. Video Only is an explicit setup choice. | A flash/clap remains aligned at the receiver across cuts, embedded signal loss/return, reconnect and a long run. Audio works with recording and meter views closed. |
| 5. Wire the native controls | Own session state in the app model layer. Expose a small snapshot and actions through the existing presentation, commands and status-popover path. Keep the destination profile and key together in the app’s private Keychain, using a separate service from camera credentials. Persist only the profile identifier in preferences. Redact destinations in errors, logs and diagnostics. Apply edits to the next session. | UI verification covers first setup, ready, connecting, live, reconnecting, missing input and failed states. Inspect compact status layout, Settings tab fit, keyboard navigation, VoiceOver and menu-only operation. |
| 6. Harden and qualify | Retry transient transport loss with bounded backoff, for example 1, 2, 4, 8 and 15 seconds, then offer Retry. Treat credential rejection as actionable immediately. Cancel retries on Stop and discard stale callbacks by session generation. After reconnect start a fresh publish with codec headers and a keyframe at the live edge. Keep last error, sent bitrate, last video send, drops and audio gaps in Diagnostics. | An independently decoded stream resumes after a network interruption. Rapid Start/Stop/Start, quit while reconnecting and invalid keys leave one or zero publishers as requested. |

The current Program route has one output contract and one active flag. Its fan-out runs **after** conversion and cadence selection, and it aggregates failures as camera queue failures. Simply adding a second queue there would inherit the camera’s contract and misattribute congestion. Keep per-destination drops, delivery freshness and failure state when extracting the shared selection path. Preserve the existing Program monitor callback and its cut-generation semantics. In automatic mode, keep the current warm-source policy for cuts plus the chosen embedded audio feed. Release only stream-owned demand on Stop. ## Release checks

- Run existing Program cadence, demand, failover, stage-retention, output route and camera-path checks alongside new stream cases. Cover stream only, virtual camera only, both startup orders, both shutdown orders and simultaneous ISO recording. Separately, with recording off, window closed and no camera client, verify automatic cuts between two visibly distinct sources at the receiver. Remove the idle second camera during a stream and verify continued delivery and access to Stop. Run the repository test, signed build and UI verification scripts.
- Validate with a controllable local ingest and one designated private RTMPS service. Observe the receiver while cutting between different rates and sizes, including 29.97/59.94 sources, reconnecting, changing virtual-camera demand and recording ISOs. Verify audio identity, decoded color, aspect, frame pacing and monitor-overlay exclusion.
- Proposed release targets on representative hardware: short receiver checks at each exercised format, receiver A/V offset within ±50 ms at the start and end using a flash/tone fixture, no growing media queue, no additional ISO drops versus the same capture load without streaming, and idle GPU/encoder behavior returning to baseline after Stop. Record machine, inputs, workload, stream drops and measurement results. If thresholds fail, report the specific unsupported load or fix the cause before declaring support.
